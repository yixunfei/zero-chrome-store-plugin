# 手机扫码请求与返回凭据方案

> 2026-10-12 执行更新：用户已确认 docs/plan-review.md 为 P1 基线并授权开始技术验证。原文中“等待审核/未开始编码/不授权开发”等阶段描述已被本次授权取代；P1 尚未验收通过。实际证据与缺口见 [P1 报告](p1-report.md)，不把候选或原型当作真机通过。

日期：2026-10-12。状态：关键交互、平台、恢复语义和默认存储已确认，具体协议提交 [整体计划](plan-review.md) 审核及 P1 验证。会话加密返回格式是工程建议，不代表用户已单独批准。

## 1. 已确认前提

- 接受办公电脑截获本次使用的密码，重点保护其他未批准记录和整个库。
- 独立扩展密码库；Windows 11＋Chrome 优先，Android 14 为手机首验环境，无现有硬件锁；考虑 Flutter。
- 电脑允许安装扩展、不能使用摄像头，允许手机扫描电脑屏幕；二维码可承载较多信息，必要时分帧。
- 约 56 字符返回码已接受，支持手输，也允许用户自行通过第三方通信工具传入；不要求每次都手动录入。
- 电脑可看到站点域名，数百至上千条账号可使用用户选择的密文存储自动同步。
- 手机丢失时，账号仅用于下载密文，独立离线恢复密钥负责解密；已有备份时无需账号即可恢复。
- 全量密文存储由用户指定，默认 Chrome 所关联 Google 账号的 Google Drive；首次 Drive 访问仍需授权并核实实际账号。

## 2. 推荐交互：一条记录版本的解密码

为首版减少离线往返和输入体积，推荐返回**该条记录当前版本的独立随机数据密钥**，而不是把完整签名加密响应编码后要求手输。

1. 浏览器展示请求二维码，包含指定记录版本的密文、给当前手机的密钥信封、记录核验凭证以及请求上下文；必要时使用有界分帧。
2. 手机扫描，验证设备、权限、记录核验状态、版本及密文，使用硬件保护的私钥打开当前记录密钥信封。
3. 手机从密文读取可信的站点/账号，显示请求设备，要求用户逐条确认。禁止由电脑提供一段未验证文本来冒充可信账号说明。
4. 批准后手机显示该记录版本的解密码，并提供修改提醒选项。
5. 用户把解密码输入或主动粘贴到扩展自身页面；正常扩展按预期记录及版本验证 AEAD，解密并填充，之后不持久化密钥和明文。不能在网页表单内接收解密码；在完全受控电脑上，扩展自身页面也不能阻止管理员观察。

已接受的码长预算：256 位随机密钥的无填充 Base32 编码为 52 个字符；再加入约 4 个错误检测字符，总计约 56 个字符。分组展示并使用避免易混字符的编码；最终编码、校验规则和输入体验通过原型确定。校验字符只用于发现输错，不作为加密认证。

本方案使用标准记录 AEAD 与标准公钥信封。人工编码是传输方式，不另造密码算法。协议仍需评审，不能因为使用了标准算法就视为已审计。

### 通过通信工具传递：推荐额外提供会话加密格式

用户允许通过第三方工具传入返回凭据，不等于要求插件接入这些工具、自动发送消息或自建中继。手输路径继续支持完全离线；用户选择联网通信工具时，该次回传自然经过网络。

推荐提供两种明确区分的返回格式：

| 格式 | 使用方式 | 安全边界 |
| --- | --- | --- |
| 约 56 字符单条解密码 | 手输；也可由用户自行复制传递 | 内容本身就是该版本数据密钥。接收方、聊天备份或同步剪贴板若同时取得对应密文，即可解开该版本 |
| 会话加密响应（工程建议） | 手机复制密文文本，用户通过选定工具转送并粘贴到扩展 | 只加密给本次请求的临时浏览器公钥，通信工具无需可信；文本通常更长，按真实编码实测，不承诺约 56 字符 |

会话加密响应复用标准 HPKE，建议只返回用户名/密码等本次需要的字段，不返回数据密钥。手机签名绑定完整请求摘要；请求含库、设备、记录、版本、密文摘要、动作、随机挑战与临时公钥。扩展验证手机签名、会话和记录上下文后解密；正常客户端拒绝错会话、重复使用和超时响应。

这一格式减少通信渠道看到单条秘密的机会，不改变受控电脑能截获最终密码的边界。恶意电脑可以保留自己的临时私钥和响应，超时不使已经取得的秘密失效。不得把“会话加密”描述成对获批电脑强制一次性使用。

两种格式使用不同的显式格式标识和解析路径，自动识别只负责解析，不能把加密响应悄悄降级为原始解密码。分享时优先会话密文，原始解密码仅在用户明确选择时复制；不自动发送、不读取聊天记录、不后台监听剪贴板。复制后清理应用控制的暂存是尽力措施，不能保证删除第三方或系统历史。

二维码可以更长，因此可携带完整请求和临时公钥；仍需限定消息尺寸、分帧上限和解码资源。不能把更大载荷理解为单张二维码具有无限容量。

### 初始配对与新增记录

无电脑摄像头也必须完成初始公钥交换。建议手机通过选定存储提供仅含公钥的设备登记文件，扩展导入并由用户在手机与电脑核对公钥指纹；手机扫描电脑配对二维码，登记电脑公钥与权限。这是初次设置/密文同步的一部分，不参与后续每次离线授权。若初始化也禁止网络，则需允许一次性公钥文件传递或手工公钥录入，不能把双向扫码当作隐含前提。

公钥登记文件被替换可能使后续新密码加密给攻击者，因此首次指纹核对、密钥固定和更换提示属于必要步骤。账号登录不能替代对手机公钥的核对。完全受控电脑仍能窃取它自己创建的新密码，方案不保证新录入秘密对输入设备保密。

浏览器保存新记录只需已核对的手机公钥，记录先标为待核验。手机首次审批时核验站点/账号，并将签署的记录摘要及版本检查点保存在手机；可在后续密文同步时发布签署凭证。在离线首次核验当次，手机依靠本地记录，不要求用户再手输一份签名。未发布凭证的记录不能在其他手机上被误认成已经核验，新增手机需可信迁移或重新核验。

## 3. 保证与限制

### 保证目标

- 每条记录、每次内容更新独立生成数据密钥。输入 A 的当前解密码不能解开 B，也不能解开 A 的未来更新版本。
- 浏览器只持有手机和恢复收件方的公钥，不能从整个密文库推导未批准记录的数据密钥。
- 手机是审批执行方；拒绝记录、设备和批量请求的策略在手机执行。
- 手机不输出任何整库密钥、设备私钥、恢复密钥或 TOTP 种子。

### 必须明确的限制

- 返回码是**当前记录版本的可重复使用秘密**，不能称为一次性动态码。正常扩展可以限制输入窗口，但恶意电脑仍可保留并再次使用。
- 扫码请求可以使用挑战、设备签名、版本和手机本地状态来防替换与重复提示；返回的数据密钥本身不绑定某一次挑战，也不具有加密意义上的到期时间。不声称返回码具备挑战响应签名的全部性质。
- 输入返回码的电脑能解密该密钥保护的整个 payload。因此首版凭据 payload 仅含用户名、密码和必要匹配字段；TOTP 种子、恢复码、私密备注等如果后续加入，必须使用不同的数据密钥和授权单元。
- “填充”与“显示”是正常客户端的动作选择，给出密钥后无法从密码学上约束恶意电脑只能填充、不能显示或导出该条。
- 查看手机屏幕、录制手输码或控制电脑的攻击者可以获得当前条目；这是用户已经接受的单条暴露边界。其他条目仍由各自独立密钥保护。
- 手机仅能验证记录身份和权限，不能验证受控电脑真正打开了哪个页面。新保存记录在受控电脑生成时也可能被截获。

## 4. 为什么不继续用 6 位码

6 位十进制码只有 1,000,000 种可能，约 20 位熵。若它直接决定某条持久密文的解密能力，持有密文的攻击者可以离线尝试，桌面输入次数限制无效。

把 TOTP 种子放到桌面以本地验证，也会让攻击者自行产生码或跳过验证；加盐不会增加短码的秘密熵，昂贵 KDF 也不把它变成高熵密钥。若桌面本就能解密、只是 UI 要求验证码，则不能满足当前威胁模型。

在线可信验证方可以限制猜测，或手机可通过网络送出高熵加密响应，使 6 位码只承担定位/确认作用。但用户已选择离线扫码加长返回码，因此首版不依赖此路线。

用户已接受约 56 字符，首版不另引入 128 位短码套件或普通 6 位码回退。通过工具粘贴不要求压缩到手输码长度，可采用上述完整会话加密响应。

## 5. Flutter 与手机安全边界

建议采用 Flutter/Dart 共享界面、交互状态、提醒与非敏感业务，Android 使用 Kotlin 原生模块封装 Android Keystore；后续 iOS 通过 Swift 原生模块对接 Keychain/Secure Enclave。

“考虑 Flutter”不表示所有密码操作都放进 Dart，也不表示 iOS 已完成支持。以下边界需要保留：

- 长期签名/解密私钥在平台安全设施内生成并保持不可导出，Flutter 只调用明确的操作接口。
- 生物识别应绑定真正的密钥使用授权；不能只依赖 `local_auth` 返回的布尔值作为密码学边界。
- 本条数据密钥需要显示成人工返回码，因此会短暂进入应用可见内存，不能声称它全程不离开安全硬件。硬件保护的是长期私钥及受限调用。
- 对 Android 的硬件能力、认证约束和 HPKE 所需 KEM 接口进行真机验证；没有硬件能力时明确失败或报告实际等级，不静默降级。
- Dart/JavaScript 的托管内存不提供绝对及时擦除保证，降低驻留时间并避免日志/崩溃上传中的秘密。
- iOS 的硬件调用、构建、签名与发布需要 macOS/Xcode 和真机；Flutter 不能消除此要求。

### 平台支持建议

- 首次验收：Windows 11 当前稳定版 Chrome＋Android 14 真机。用户要求 Android 统一版本可用，按同一套应用覆盖支持的系统版本理解，不按手机型号维护不同业务实现。
- 候选最低版本：Android 12/API 31，以便使用公开 Keystore ECDH 接口；先验证 14，再覆盖拟支持的其他稳定系统版本。最低版本是待验证的工程建议，不是用户已经要求支持全部旧 Android。
- 系统版本、厂商硬件和具体认证组合分别检测。同一应用不意味着所有设备的 StrongBox、TEE 和密钥认证能力完全一致；缺少要求的能力时显示明确不支持，不静默降低安全等级。
- 手机型号不再作为完成当前产品规划的前置问题；进入硬件验证时记录实际测试设备。Chrome 扩展与 Android 使用统一协议和格式版本；Firefox/iOS 后续使用同一协议，分别验证平台实现。

## 6. 同步方案调整

由于用户要求数百至上千账号，完整密文库应由选定的加密文件/对象存储承担，浏览器 `storage.sync` 只同步小型配置、库标识与不含秘密的连接提示，不再承诺装下全量记录。

浏览器 OAuth 令牌、WebDAV 密码等存储访问凭据仅按设备管理，不写入浏览器同步。受控电脑仍可能取得该设备的存储令牌、复制或删除密文；手机密钥隔离保护机密性，独立备份和版本恢复保护可用性。

离线授权与联网同步分开：记录在本地缓存后，扫码与手输解密不依赖网络；密文同步需网络。手机可直接从请求二维码取得本条密文，不必为了每次授权访问云端，也不必先下载完整密码库。

Chrome/Firefox 可通过同一个选定存储交换相同密文格式；首次存储授权和手机配对仍按设备执行，不能把“同步扩展设置”误认为“所有账号权限已自动迁移”。默认 Google Drive 已确定；建议以 HTTPS WebDAV 提供首版可配置存储，细节见 [存储与恢复](storage-and-recovery.md)。

匹配目录建议独立加密并由手机在配对时授予电脑目录密钥；此密钥只打开域名/非敏感别名，不打开凭据。电脑允许持有目录访问能力，云端仅存目录密文，手机仍从当前记录可信内容核对账号。

## 7. 已确认的恢复目标

用户已选择下表第一种：账号仅下载密文，恢复通过独立离线密钥。第二种仅保留作边界对照，不进入首版。

| 模式 | 实际保护 | 成本与限制 |
| --- | --- | --- |
| 账号取得密文备份＋独立恢复密钥/口令 | 云账号控制备份下载；独立材料控制解密 | 可不自建恢复服务；密文一旦被复制，离线解密不再需要账号；浏览器账号名不是秘密 |
| 账号重新验证＋在线秘密释放＋独立恢复材料 | 缺少在线释放的一份必要秘密时无法从备份直接恢复 | 需要可信服务参与密钥释放，增加可用性、审计和账号提供方依赖；普通云盘文件权限不等同于该保证 |

在扩展 UI 中先检查“浏览器已登录”再执行本地解密，不是不可绕过的第二因素。Google/Chrome 身份 API 与 Firefox 的外部 OAuth API 也不是统一的浏览器同步账号认证接口，需要明确实际使用的账号提供方。

即使选择在线强制恢复，也不能撤回合法恢复后已留存的密钥或密码。常规恢复必须在可信手机/可信环境执行。

## 8. 整体评审与技术验证

1. 产品选择已确定：离线恢复、默认 Google Drive、约 56 字符、Android 14、Windows 11 和 Chrome 优先，不重复询问。
2. 会话加密返回格式、Flutter/原生模块、Android 12+ 下限、WebDAV 和目录授权作为具体工程建议随整体计划审核。
3. 扫码载荷、硬件密钥、Google OAuth 与同步故障仍需原型验证。当前不宣称实现已经可用。
